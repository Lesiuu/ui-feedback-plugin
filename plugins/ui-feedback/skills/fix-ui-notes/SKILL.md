---
description: Works through the UI notes a person left on their running site in the UI Feedback board, and hands the repo's design system to the board so pages are checked against it. Use when asked to fix UI notes, UI feedback or design review comments from the board, or to set up or update the design system on the board, or to check pages on the board after a UI change.
---

The notes live in the person's open UI Feedback board tab and reach you through the `ui-feedback` MCP server.

0. Once per session, before the first round, call `set_site_identity` with the repository's name and its git remote (`git remote get-url origin`), when this repository serves the site the board has open. Ports are reused, and this keeps another project's notes on the same port apart from yours. If a tool answers that the board is waiting for the person, ask them to answer on the board. Then call `get_design_system`. If it says nothing is stored for the site, read the design system from the repo and hand it over with `set_design_system`: the palette (name, value, role, light and dark), fonts with their weights and intended use, the type scale, the spacing scale, radii, shadows, breakpoints and the general rules. Look in the Tailwind config or the `@theme` block, the CSS custom properties, a design tokens JSON, a theme file, `DESIGN.md` or a brand guide. Send resolved values under the names the code uses, and add `check` and `value` to rules a script can judge (see the tool's schema). Call it again when the design system changes. The board then checks pages against it, and what is off comes back as `Check:` notes that name the token to use. Follow the stored system, rules included, in every UI change. `get_design_tokens` shows what the rendered pages use now. None of these calls starts a round.
1. Call `list_notes` once at the start of a round. It hands the notes over: the board records how the pages look now, so your changes can be reviewed against that. Filter with `url` (a page path such as `/pricing`) or `status` (`open`, or `again` for notes sent back as still wrong) only when asked to. Run `git rev-parse HEAD` before your first change and keep it as the round's `base`.
2. Fix each note in the source code. A note gives the page, the screen sizes, the element (selector, HTML excerpt, styles) or the quoted words and often the source file and line. Notes sent back as still wrong say what was already tried and, when you committed it, the commit of the previous attempt (`git show` it if you need the details), so try something else.
3. After each note, call `resolve_note` with its number, `status` (`fixed`, `skipped` with the reason, or `question` with what you need to know), a one-sentence `summary`, the `files` you changed as `path:line` and the `commit` when you committed the change. Notes with the same outcome can share one call.
4. When you are done with the notes, call `end_round` once with the last `commit` of the round (leave it out if you did not commit), the `base` from step 1 and a one-line `message`. Never pass a diff: the plugin adds it from git.
4a. To see a change through the board's eyes, call `check` with the `paths` of the pages you changed (and `devices` such as `phone` when the change is for one width). It runs Check site on the board and answers one line per cause, then on the next call what got fixed and what is new. `more` with the `cursor` it ends with gives the rest, `more` with a `finding` such as `f3` gives one in full. If it says the check is still running, call `check` again. If it says the board is in a background tab, ask the person to bring the board's tab to the front. It never clicks on the page and starts no round.
5. The person reviews your changes on the board and accepts them or sends them back. When they say they have reviewed, call `get_review_state` and, if anything is still wrong, start the next round with `list_notes`.

If a tool answers that no board is open, ask the person to open the board in their browser. If it answers that the board has no such tool, ask them to reload the board tab. If the server asks for authentication, ask them to run `/mcp`, pick ui-feedback and choose Authenticate.
